# TV Director × short-drama 完整融合实施方案

版本：**设计 v2.1，2026-09-25**。这是待实现合同，不是完成声明；本次修订只修改文档，没有运行新生成或产生模型费用。

## 1. 目标、边界与权威文件

目标是独立实现 Liblib.tv TV Director 的完整可观察产品：画布与剧本节点、浮窗/停靠、全能创作、原创/改编、导演执导、设定器、对话和审批、版本化编辑、Skill 生命周期、媒体任务、历史/分享/插件/恢复。用 short-drama 的原创、改编、事件、因果、逐集闭环和可拍性方法支撑内容质量，不套用旧“虾本”四阶段页面。

不能由输出唯一还原第三方私有系统提示词、Skill 文件、隐藏检索库或模型配置；本方案实现的是独立方法与可验收行为，不承诺逐字相同。品牌、头像、示例图换成自有资产；生产环境不依赖 LibTV 私有接口。视频模型保持仅 MiniMax H3；文本模型使用配置中**实际可用且路由一致**的模型，不凭可输入的型号推断可用性。

下列五份合同与本文组成同一 v2.1 规范。每项规则只在指定文件定义，旧开发方案的冲突段落不再作为实现依据。

| 权威文件 | 唯一负责的内容 | 开发前必须得到的产物 |
|---|---|---|

## 2. 证据等级与当前实际能力

| 标记 | 意义 | 不允许的推论 |
|---|---|---|
| S | short-drama 可读方法与参考文件 | 读过不代表软件已经执行 |
| U / C | LibTV 界面 / 正常加载的客户端分支 | 有按钮或代码不代表该分支已成功实测 |
| R / T | 捕获请求返回 / 指定样例完整闭环 | 一个样例不代表全部题材、长篇或异常分支 |
| I | 我方独立设计或有意改进 | 不冒充 LibTV 内部实现 |
| N | 未实测或不可见 | 不用模型猜测填成已证实 |

源站十项补证已实际推进，不能再把整类长稿、Skill、批处理、分享或Plugin统一写成未测。最新T/F/N按[验收合同§6](tv-director/acceptance-contracts.md#6-源站十项补证逐子项结果不整项虚报通过)及[补证报告§13](tv-director-liblib-gap-validation.md)逐子项读取：既有成功，也有真实失败与明确未测。未可观测/未测试部分已在[收口与实施清单](tv-director/implementation-closure.md#7-所有源站未知失败项的固定处理决定)U01–U13定义独立实现规则、负责人职责、阶段和发布门，不再交给实现者猜；不把设计决定冒充源站T。

当前代码只有独立 Director 首切片：作品/文档版本/待审稿、部分浮窗/设定/编辑器，以及真实 V4-Flash 原创大纲和分集草稿。30 秒样例过密，未人工定稿；阶段方法、来源事件、完整状态机与全功能尚未落地。**生成接口成功不等于质量通过，更不等于全产品完成。**

short-drama 用户源目录与安装副本本轮逐文件核对，24/24个文件SHA-256一致；[来源清单](tv-director/source-inventory.json)保存相对路径、hash及阶段路由，不含本机绝对路径。方法参考来自该快照。进化快照 schema v2 / knowledgeVersion `2026.09.23.4`，`ruleCount=0`、`exemplarCount=0`；只能声称融合静态方法，不能声称已融合“验证案例库”。源文件hash已冻结；后续方法包的独立版本也须记录实际打包hash，不以本机绝对路径作运行依赖。

## 4. 融合原则与有意差异

不把 short-drama 所有通用建议升级为强制规则。用户明确要求、锁定事实和当前获批规格出现互相冲突时，必须停在有具体选项的冲突卡，不能默默以“新要求优先”篡改旧作；用户确认修订后才建立新规格版本。安全、权限、资料范围及费用授权始终由代码约束。

| 方法或源站行为 | 本产品决策 | 分类与理由 |
|---|---|---|
| short-drama 默认50–100集、三幕、固定高潮/付费比例 | 用户集数/结构/目标时长优先；商业卡点仅在启用付费叙事策略时适用 | I；避免把1×30秒写成百集模板 |
| 每集新钩子/下集预告 | 非末集需兑现当集目标并衔接；末集按结局收束，可开放但不强造“下集” | I+S的条件化融合 |
| 4层反派、3–5场、3种景别、5秒开场 | 作为题材/时长可适配建议，非机械硬断言 | I；温情/纪录片/极短片不能被爽剧模板污染 |
| 改编设定器最小2集、后端问卷可1集 | 统一允许单集，来源 EP02、交付标签与工作流序号分开 | 有意修复，不声称原站表单也如此 |
| 某次末集自动 completed，另有“改/定稿”卡 | 全部集默认明确人工定稿；可批量授权“生成”，不可隐含授权“质量定稿” | I；证据分支不一致，不照抄危险的自动完成 |
| 原站预算提醒、自动审批 | 提醒与硬上限分开；我方必须有硬上限与预留账本 | I；保护从方向到媒体的真实费用 |
| 展开思考过程 | 只展示阶段、调用、结果与简洁进度，不展示内部推理 | I；可解释不等于公开推理轨迹 |

这些差异应出现在兼容性验收中，不能一边采用改进，一边宣称像素、流程、默认值完全一致。其余观察到的布局和操作遵循基线；未知处先实现明确的自有合同并补证，不称“已复刻原站内部”。

## 5. 实施顺序：费用、权威数据与反例先落地

以下是依赖顺序，不是仅靠时间到点就进入下一步。每片都要先更新任务台账/精确 scope，旧模块保持兼容；建议文件是未来拆分位置，**不表示这些文件已实现**。

| 阶段 | 明确交付与代码落点 | 退出门与依赖 |
|---|---|---|
| P0 合同与基准数据 | 五份合同；匿名 `tests/fixtures/director/`；按钮参数表、正负例、schema快照 | 按验收合同建完整清单，先跑可离线反例；N项有证据计划与预算，不能冻结假事实 |
| P1 权威模型/运行安全 | `director/models.py`、repository/migrations、document_ast、events、runs、approvals、cost_ledger、outbox、provider ports | AST/版本/CAS/状态、预算预留、幂等、UNKNOWN、恢复、旧数据迁移先过；禁止此门前做真实收费链 |
| P2 方法编译器/原创 | `skills/registry`、`rules`、`context`、`workflow`、`tool_registry`、`planning`；API由schema生成TS | M01/M03/M07–M11/M22/M23串联；方向→总纲→逐集→人工定稿→续集；1×30秒/2×30秒及费用全链通过 |
| P3 来源/改编 | `source_ingest`、`source_audit`、`event_graph`、`adaptation`；M02/M04–M06/M24 | 多源、跨块、别名、独立漏检、四策略；原稿集号保留；关键事实来源可定位 |
| P4 质量/时长/修订 | `duration`、`review`、`revisions`、`dependencies`；M12–M15 | 并行时长、评审不可用、限次修订、部分依赖组、全剧风格/集数/语言变更；定稿失效正确 |
| P5 完整剧本界面 | `frontend/src/features/director/`拆组件与纯编译器；独立canvas适配 | A/O/D/Q/S/E及X基础交互，浮窗/节点/双栏/融合/编辑器/问卷/报价/历史双视口，三语与键盘路径 |
| P6 Skill/导演/全能 | M16–M21；Skill repository/intake/evaluator，director/canvas adapter | R/K、角色/Skill全生命周期、上下文快照、批处理、画布事务、跨模式恢复；未接入媒体不得伪完成 |
| P7 媒体/生态/交付 | H3 capability/compiler/ports；插件/分享/export/backup恢复 | C全能及媒体、A06/A08/K发布、Windows、权限、网络失败；账本复用P1，禁止另造审批链 |
| P8 全产品对标 | 全部测试、真实匿名样例、差异清单与剩余N | 完整按钮/能力零遗漏，质量与视觉门均通过，P0/P1级缺陷清零；未验项不能写“完整等价” |

P2并非跳过质量门：M10/M12的基础容量、事实/连续性检查、限次修订与人工定稿必须随原创链一起落地；P4是在此基础上补复杂并行排程、跨文档/跨集修订与完整回归，不是等P4才发现超时。P5才统一视觉收口，但P2起已有可真实操作的最小UI/问卷/费用卡供验收，不能只用CLI声称用户链路通过。

CE首版维持独立 director 域 + 项目 state_dir 下 SQLite；不按旧研究原型另搭 PostgreSQL 项目。模型和媒体通过 ports/既有可审计网关，路由保持薄。共享导航、画布、翻译的变更需单独 scope 与协调；前端 token 与 DESIGN 同步。业务实现需要的依赖版本在该片开工时查官方文档、锁定后测试，本次不擅加依赖。

旧实现不是重写起点也不是可直接宣布复用完成的底座：逐字段迁移已有作品与源绑定，旧正文作为 legacy_unverified 保留，旧固定参数冻结需迁移为可审的 SpecChangeSet，不能为支持修改而直接解除保护。模型网关实际ID校验保留；缺少账本/事件/质量门的旧成功 run 不补造费用或PASS。

## 6. v2.1 收口交付与完成定义

开发接手顺序：先读[代码级收口清单](tv-director/implementation-closure.md)，再按对应五份合同实施。该清单含当前代码改造、类型展开、184语义命令的边界、22个工作包、迁移/回退与13项证据差异决定。

[机器追踪表](tv-director/implementation-map.json)将149动作、8能力、24方法、18规则、33转移、33类fixture和482个计划测试ID连接到精确代码位置；[规格检查器](tv-director/verify-spec.mjs)验证编号、引用、来源与状态，且用反向突变防止漏项/假PASS。这些是计划与规格检查，不是业务测试结果。

### 完成定义与下一步

文档完成与软件完成分开。本次设计修订完成的标准是：九项问题有唯一合同、按钮/Skill/规则有具体输入输出和失败处理、旧矛盾已消除、链接/编号/安全/guard通过。软件完整目标则必须通过专项验收合同全部门，并附真实证据；不能以本次文档修订、几个通过的单测或一次V4返回代替。

下一步代码工作从 P0 的可执行夹具与 schema 开始，再实现 P1。先让“读完仍漏关键事件、手改正文旧图未失效、部分采纳断依赖、末集自动完稿、断网重复扣费、声画并行估时”这些负例稳定失败，再逐项修正变绿；之后才继续真实模型质量对比。源站未证实分支按收口清单U01–U13的决定实现与验证，软件发布前按对应门拿实际证据；不重复花钱证明已经知道的路径，不需要等到获得第三方隐藏代码才能开工。
