# LibTV TV Director：按钮级功能、协议与 Skill 研究报告

取证日期：2026-09-24。研究对象为用户授权账户实际可见的 [LibTV 画布](https://www.liblib.tv/canvas)。

> 研究范围是完整 TV Director，而不只是剧本生成框。目标产品是全新独立系统，不以本仓库现有实现为约束。本稿持续补入测试结果；没有实测的分支明确标注，不把前端常量、模型自述或预期行为当成已通过验收。

配套：[技术开发方案](liblib-tv-director-development.md)。原始浏览器请求、返回、截图、测试原稿只保存在已忽略的 `output/playwright/liblib-tv-director/`，不得直接提交。

## 1. 核心结论

1. TV Director 是「模式路由 + 持久会话 + 工具执行 + 文件工作区 + 人工确认 + 画布操作」的组合。聊天文本只是其中一个视图。
2. 原创和故事改编使用同一个剧本 Agent，但预设和服务端工作模式不同；全能和导演执导各有独立 Agent 标识。
3. 已实际跑通原创方向确认、大纲及人物/关系/场景/道具写入、首行局部改写与接受后刷新，以及独立研究小样的单集闭环。新增独立两集样例：预设覆盖顺序、全剧大纲修改与差异采纳、第一集人工验收、第二集续写、自动评审修订、全剧完稿和刷新留存均有 UI 与协议证据。四类改编方向均完成原稿分析与方向建议；自建导演角色保存和复用成功。《非妖哉》EP02 另做真实单集原稿改编正文试验；完成读源、问卷、报价、写作与修订，但产物未过独立事实/时序审查，未确认定稿。
4. 不能概括为“全部免费”：两集样例逐集返回 `power:30, originalPower:30, free:false`，手动批准两次；同一测试标签页刷新后余额由1,110→1,080→1,050。此前单集样例另有1,140→1,110的观测。报价与可见余额变化相符，但未取得内部结算账本。
5. 前端和普通业务返回足以还原大量 UI、协议和工作流；不能据此保证取得服务端全部 Skill 原文、系统提示词、模型权重或内部路由。能够开发行为相当的独立实现，不能承诺一次复刻就有完全相同的生成质量。
6. 公共 Skill 卡片描述、导演角色 Skill、剧本链 Skill 是不同层次。公共卡片不等于后台完整工作链。

对用户所问六项的当前结论（「已实测」只指所列样例）：

| 事项 | 当前证据 | 尚不能声称 |
|---|---|---|
| 调整剧本逻辑 | 两集总纲上的跨集因果修改→`skeleton.md` 待审差异→全部接受→后续单集沿用；另有首行局部修改实测 | 已写完两集后做全剧关联修改的自动传播和冲突处理 |
| 整个剧本结构 | 三幕式、两集各30秒的参数实发；大纲含分幕、单集骨架、伏笔回收、创作禁区；全剧完成状态实返 | 长篇切章、六集以上的阶段结构和所有题材都遵循同一阈值 |
| 风格设置 | 都市写实作为 `visualStyle` 实发；切换Top8时本次画风保留，集数/结构重置 | 成稿后改画风是否重写全部文档/影响角色图与媒体 |
| 界面操作 | Top8双栏、集数滑块1–100、结构/画风弹层、聊天三题、报价、总纲差异、剧本节点与编辑器已操作 | 全部按钮、极窄屏、断网、多设备和所有特殊状态均已验收 |
| 集数设置 | 2集从设定器、`scriptPreset.episodeCount="2"`、问卷、`finish_script_task.total_episodes=2` 到两份正文一致 | 完稿后增加/减少集数及其历史版本迁移 |
| 第一集后的续集与收尾 | 第1集交付→人工确认→第2集独立报价/批准→骨架/正文/评审/修订→`stage=completed`，刷新仍在 | 任意N集、失败重试和跨设备续写都与本样例完全等价 |

## 2. 证据等级与测试边界

| 标记 | 含义 | 可以支持的结论 |
|---|---|---|
| U | 真实 UI 操作或截图 | 按钮、状态、可见校验、布局 |
| C | 浏览器正常下发的客户端代码 | 序列化、默认值、事件处理分支；不代表服务器采用了该值 |
| R | 真实请求与返回 | 实际参数形状、返回状态、事件顺序 |
| T | 输入—操作—返回—产物完成闭环 | 该样例下的实际行为；不外推为全部场景 |
| I | 根据上述证据推断 | 新系统设计建议，不能声称是原产品内部代码 |
| N | 尚未验收 | 必须保留测试任务，不可标成完全复刻 |

用户提供的两个入口均已观察到已有单集剧本文档；其中一个被其他标签页占用，出现会话过期/刷新提示。为避免覆盖原稿，正文研究另建独立测试项目。打开已有剧本编辑器会建立或关联剧本会话，不能理解为“打开编辑器绝无任何写请求”；原稿内容未修改。另在原项目的独立新对话观察了导演角色创建入口，未向其发送原稿正文。

## 3. 页面与交互结构

### 3.1 容器

画布保持在背景，TV Director 可以浮窗或停靠右侧。浮窗有八方向尺寸拖拽，顶部为会话标题与操作区，中间为流式消息/工具卡/问卷，底部为富文本输入与模式参数。全屏剧本编辑器与聊天并非同一块文本框；文档交付卡可以打开对应文件。

欢迎区按画布上下文变化：空画布显示“选择 Skill 开始创作”“批量创建分镜”；已有节点时显示“感知画布开始创作”“批量优化提示词”。原创与上传改编是共用快捷入口。

文档类型在客户端包括 pdf、txt、md/markdown、doc/docx。上传后的消息携带 document 部件，而不是把整篇正文直接塞进 preset。服务端将附件转为可读取的源文路径。

已实测的改编链：

```text
附件 + preset(adapt/剧本浓缩/2) + 用户要求
→ init_work(mode=adaptation, source_file, work_key)
→ split_source()
→ read_source(chapter=1)
→ 原文分析、不可更改事实、容量判断、4个叙事方向
→ ask_human(方向/集数/时长)
```

`split_source` 返回 detector、segments（index/title/start_line/end_line/chars）与 warnings。短文没有多章标题时仍继续单段，不直接卡死等用户修格式。`read_source` 返回带原文行号的正文，并告知行号只用于切分定位、不得复制进剧本。工具返回提及 `cut_chapter(cut_lines)`，但本轮尚未调用它，不能声称切章落点已全面验收。

浓缩样例明确保留两个人物、父亲不出场、现实背景、借伞结尾；给出的四个方向分别调整悬念、人物情感、对话机锋和物件母题，而非随意生成四个新故事。方向建议和成品正文仍是不同交付阶段。

扩写样例在同一原文上列出8项可拍动作补充和4项因果补强，仍保留原角色及结尾。测试提示词额外要求解释新增动作，因此这是同源策略对照，不是只改变一个 preset 的严格控制实验，不能把全部输出差异都归因于按钮。

强化冲突试验发现真实保护分支：`init_work` 返回 `success:false`，错误说明 work 已属于另一会话、禁止继续写入，要求中立询问“继续编辑已有作品 / 新建一部作品”。选继续时应 handoff，提示中使用作品标题而非内部路径；选新建时再次 init_work，必须使用错误返回提供的新 work_key，不得由模型另造。已实际选择新建，保留了冲突与反馈全过程。

扩写与冲突两次都观察到标题生成异常：`get_title_by_message` 返回了长篇分析式标题，且虚构了附件没有的母女/父女故事。主聊天扩写分析正确读取并使用了原稿人物，不能把标题错误混同为主工作流读源失败。新系统需将标题摘要与创作结果隔离，限制长度并做来源校验。

冲突强化最终主回复正确保留阿宁/阿禾，给出制度、内心、时间、信任四种阻力方向，并比较目标/阻力/代价。它也新增了“锁单后自动赔偿”“值班员垫钱/担责”等原稿没有的制度设定；这些是改编建议，不应在新系统中无标记升级为原文事实。两人、不让父亲出场等硬限制通过，不代表对现实制度的所有推演都自动可靠。

### 5.1 钩子分支首次失败（R，不计成功）

首次 `init_work.source_file="uploads/<id>.txt"` 漏了空间前缀，初始化却返回ok；随后 split_source 明确 not exist。再次以完整 `<space>/uploads/<id>.txt` 初始化同一作品，返回 already_initialized，并没有更新原稿绑定。read_source 再报尚未切章。最终主回复承认无法分析并建议重建会话，没有凭标题补出不存在的原文。

这证明 `ok`/`already_initialized` 不是端到端读源成功。复测另开会话、重传同一附件并在提示词中要求检查完整来源路径；复测有人工提示介入，结果必须与初次失败分别统计。禁止把程序缺陷简单归因于用户“文件有问题”。

复测最终完成：正确读取339字原稿，给出解谜反转、轻喜错位、治愈情绪、倒计时快节奏四方向；每个方向列出两集的开头钩子、集尾问题及后续兑现位置，最后停在方向/集数/时长问卷。正文未生成。模型提出“20秒约70–80字对白加4–6画面”等容量估算，这是输出中的建议，尚无实际朗读/成片测时，不能直接成为时长验收依据。标题接口再次生成了偏离原稿的长文本，主分析则正确使用两名原稿人物。

### 5.2 四方向同源对照小结

| preset | 本次输出重点 | 已证实到哪里 | 不能据此声称什么 |
|---|---|---|---|
| 浓缩 | 信息取舍、悬念/情感/对话/物件四取向 | 读源与方向确认 | 尚未验证最终正文实际更短 |

#### 修改确认关口与第二轮复核（U/T，未定稿）

平台在首次稿末尾显示「第二集样片是否确认定稿？」与「确认定稿 / 要改」。本次明确选择「要改」，在输入框提交逐场问题；界面将意见绑定到该问卷，随后返回逐场差异、修改过的正文及大纲文档卡。正文修改为待审差异，人工点击编辑器的「全部接受」才使正文生效；这一步**不是**“确认定稿”。大纲文档当次打开时没有相同的待审工具栏，故不推断所有文档都使用同一种审批合同。之后第二次发送剩余问题，进入新的无自动生成修订轮，未再批准正文报价。

第二轮稿修复了先前的三项大缺陷：小画先被黑线拖入湖、再由大郎取回；焦七带走年画并把绫娘拖回；戏楼已是深夜、点灯只照明不触发变身；夜路不再闪出白昼童。它仍未过导演审查：1-11 把手掌小画写成「画轴」；1-14 将桂娘必须说出的完整句压短；1-16 未交代大郎双手拿火把/小画时如何取针救人取画；1-19 前厅已冒烟却继续平静看戏；1-3「夜」场还出现最后夕光。大纲残留「原文第1–3章→第1集」与戏楼才入夜的旧描述。以上已作为新一轮具体修改意见提交，尚未定稿或证明质量合格。

平台估算「对白约860字＋动作转场170秒＝400–415秒」，但对本次导出的正文独立按角色台词统计约885汉字/88轮，且1-0场光对白约55字，按平台自报3.7字/秒已需约15秒，未计动作。总估时不能代替逐场预算、真人试读与分镜排演；新的逐场时长表待核验。此次反例应作为行为复刻的黄金测试，而不是把平台输出直接当黄金答案。

再修一轮后，平台给出21场估时表，宣称750字、414秒；对该轮可见正文按「角色台词引号内汉字，不含标点」独立统计为726字/89轮，表中1-1误写15字而正文约45字、1-2误写51字而正文15字，明确存在串场。该稿又把小画置于桌面、纸狮扑咬，下一场却直接回大郎怀中，缺取回动作。已在同一独立项目再次明确要求核对现稿、补动作、不靠调低秒数凑415。平台随后承认原估时表错位，新一轮自估一度得出473秒、超58秒，并提出把快剪写回正文；在改后的正文和逐场表实际核实前，不把其414秒自述视为通过。此处从一次失败到追问修复的过程，证明独立可执行校验器比 Agent 自报数字更重要。

第四轮确实把12处「快剪」写进正文，并给出另一张21场表，合计仍自称726字/89轮、414秒；这不是拍摄实测。该表的1-1写44字、1-3写58字，与从本轮正文解析出的1-1约45字、1-3约51字仍有偏差；更关键的是1-16给10秒动作预算，却同时安排入宅、安放两件道具、细针解救、取年画、纸狮成形、冲突、起火与塌顶，缺乏可执行节拍证明。其补的「从干桌取回小画」放在已切到街巷的1-17开场，空间上仍错位。故只保留为未采纳的研究草稿；本机另有把取回动作移到宅院塌顶前的导演工作稿，但不宣称已达到415秒或平台已定稿。真实通过门须逐镜动作时长、试读和人工审阅，而非增加「快剪」二字。

## 6. 原创的真实检查点与文件产物

```text
新剧本占位节点 → 创建/关联 session
→ init_work → direction 等待用户
→ 大纲 skeleton.md + 结构化 plan
→ characters.md / relations.md / locations.md / props.md
→ finish_script_task → outline 等待用户
→ episodes_skeleton/EP001_skeleton.md
→ script_writing 报价与单次审批 → scripts/EP001.md
→ review_episode(episode=1) → 修订或显式保留评审不可用状态
→ 第1集交付/人工确认 → 下一集单独报价、审批、写作与评审
→ 最后一集 finish_script_task(stage=completed) → 全剧完稿
```

`RUN_FINISHED` 可以发生在等待问卷时，不能把一次 run 结束当成全剧创作完成。

`write_artifact` 的实测形状：

```json
{"path":"skeleton.md","content":"<本片段Markdown>","more":true}
```

后续片段：`append:true`；最后一次不带 more，并可带 title 和 plan。plan 包含 `total_episodes`、`episode_duration_seconds`、`episodes[]`，每集至少包含 episode/title/must_keep/ending。工具返回 `ok/partial/bytes_so_far/path/violations/checkpoint_note` 等字段；正式提交完成后有 display_name。

文档写入同时通过 `ACTIVITY_SNAPSHOT(activityType="write_file")` 通知界面，含 `id/name/path/operation/size/content_preview`。因此实际 UI 文档卡并不必须从助手自然语言里解析。

可见大纲包含概要、故事简述、背景规则、全剧分段、钩子、伏笔、反转、创作禁区。生成样例对短篇执行了“不拆阶段”的规则；这是样例行为，具体阈值不能仅凭一次模型输出作为后端硬规则。

### 6.1 一次有费用的正文闭环与结果质量（T/R）

在独立研究作品《最后一班电梯》上，仅提交1集、30秒、3场、不得生成媒体的请求。报价后关闭自动确认，仅批准这一次。脱敏采集可复现如下顺序：

| 顺序 | 实际动作/返回 | 可验证结果 |
|---|---|---|
| 1 | `POST /api/task/generation/power/calculator4agent`，`scene=script_writing`，`params`含 `episodeNo=1`、画布 `projectUuid`、空间 `spaceId`、作品 `workKey` 和该集 `prompt` | `code=0`、`power=30`、`originalPower=30`、`free=false`；界面显示30积分及预计1–3分钟 |
| 2 | 手动「确认生成30」，未勾本对话自动确认 | 批准后同一会话继续，而不是新建作品；确认卡消失 |
| 3 | `write_artifact(path="episodes_skeleton/EP001_skeleton.md")`，随后 `write_artifact(path="scripts/EP001.md")` | 一集骨架和正文写入均成功；并非只有聊天文本 |
| 4 | `review_episode({episode:1})` | 返回逐项评审，指出误收动作缺可见条件、楼层动线矛盾、退休处境缺正文依据；部分条目不通过，不是全绿假评审 |

```json
  "startOffset":2,"endOffset":29,"lineStart":1,"lineEnd":1,"fileName":"故事大纲"

```

这是 Markdown 首行 `> ` 后面的偏移，不是屏幕像素。此前键盘选择误选全文时标签显示1–63，已清空未发送草稿并重新精确选择首行；未把误选归咎于站点。

真实执行顺序：`read_artifact_lines(path)` → `patch_artifact(path, patch)`（unified diff，仅第1行）→ `finish_script_task`。收尾返回 `user_review_required:true`、`draft_files:[...]`、`follow_up_needed:true`；要求仅总结变更并等待审阅，**不再调用 ask_human，不继续写正文**。可见“正常检查点”与“修改待审”有不同收尾协议。

`POST .../vfs/script/diff` 返回 `{pairs:[{origin_path,change_path}],total:1}`，其中 change_path 在 `<work>_draft` 目录。前端分别读原稿和草稿再渲染差异，并非该接口直接返回每个 hunk。

原稿1629字符，草稿1631字符；逐字符对比证实仅为指定字符串前增加“都市”。接受时先 `POST .../vfs/script/write`，请求 `{projectSpaceId,path:<正式路径>,content:<合并后全文>}`；再 `POST .../vfs/draft/push`，请求 `{projectSpaceId,status:1,canvasId,sessionId,paths:[...]}`。两步都返回 code=0，整页刷新后正式稿仍保留改动。`status:1` 只在本次全部接受中已证实，其他枚举不能猜。

## 11. 传输层与接口地图

### 11.1 会话创建

```json
{
  "projectId":"<space-id>", "name":"<首条请求>",
  "agentName":"libtv_agent_script_copilot", "canvasId":"<canvas-uuid>",
  "nodeKey":"<screenplay-node>",

```

`POST https://im.liblib.tv/api/v1/project/session/create` 返回 sessionId/name/latestSeq/created。已有剧本关联还观察到 workKey。注意此接口 projectId 是空间 ID，而消息上下文 currentProjectId 是画布 UUID；新系统应更名避免混淆。

### 11.2 消息

WebSocket 上行外层 threadId/messages/forwardedProps；messages[].content 是 **JSON 字符串**，里面是类型化部件数组，不是直接对象。

```ts
[
  {type:"text",text:"{{ document:<id> }}{{scriptPreset:<id>}}<用户要求>"},
  {type:"document",id:"<id>",name:"<原稿名>",source:{type:"url",value:"<资源>",mimeType:"text/markdown"}},
  {type:"scriptPreset",id:"<id>",name:"<展示名>",preset:{mode:"adapt",direction:"剧本浓缩",episodeCount:"2"}},
  {type:"context",id:"user-context",name:"用户设定",metadata:{
    currentProjectId:"<canvas>",currentWorkspaceId:"<space>",currentNodeKey:"<node>",
    dryRun:true,agent_name:"libtv_agent_script_copilot",script_model:"seed_evolving"
  }}
]
```

forwardedProps.extra 再带 agent_name/currentNodeKey/script_model。不是所有后续消息的 metadata 都含 nodeKey，必须保留 session 与外层上下文关联，不能依赖一处字段。

下行实测有 RUN_STARTED/FINISHED、TEXT_MESSAGE_START/CONTENT/END、TOOL_CALL_START/ARGS/END/RESULT、ACTIVITY_SNAPSHOT、CUSTOM seq。工具 content 可能二次 JSON 编码，解析器需限深解码，不使用 eval。

### 11.3 前端工具执行与恢复（客户端）

存在 fe_tool_call、fe_tool_cancel、fe_tool_receipt；服务端让前端操作画布，前端返回回执。requestId 去重、取消、unsupported/error 都有分支。切换会话会处理未完成的前端执行；新系统必须解决后台会话尚有前端工具依赖时怎么办。

重连退避在当时客户端为1秒/15秒/60秒；有 seq 去重、消息回放、可见性恢复、会话抢占处理。不能把 WebSocket 重连等同重新提交任务。

## 12. 复刻边界与仍需补齐的验收

界面与协议可以独立实现高度对齐；生成内容只能通过同源评估逐步逼近。独立产品应替换第三方品牌与示例资产，不依赖其私有线上接口作为正式后端。

此前已补齐**短篇两集**的总纲修改、逐集审批、跨集伏笔回收、第二集自动评审修订与全剧完稿。2026-09-25进一步补测十类边界，最新逐子项状态见[补证报告](tv-director-liblib-gap-validation.md)及[验收合同§6](tv-director/acceptance-contracts.md)，不再把已实测的切章、完稿后风格/结构/集数、部分审核、普通Skill、批量节点、窄屏/停靠和断网全部笼统标成未知。仍有真实失败及未覆盖分支，不能把两集或合成长稿成功外推为全量验收。

### 12.1 2026-09-25首轮补证对先前推断的纠正

本小节是首轮记录；后续授权实测结果以§12.2及补证报告§13为准，不能继续把实际分享/OAuth/媒体运行标成未执行。

- **差异与依赖**：故障注入下“全部接受”部分成功；强依赖改名虽被模型声明必须9文件同时采纳，UI仍允许只接受人物标题，正式文件混名。原子组/CAS是应实现的改进，不是源站既成事实。
- **长稿与方法**：3万字符24章摄取和切成两集可追溯到392行末尾；生成规划仍违背顺叙要求。另一路Skill的read_file_v2有20000字符单读上限，不能据此误判整个剧本代理只读前2万字。

### 12.2 授权续轮的新增实证与操作差异

逐请求和费用事实唯一落点为[补证报告§13](tv-director-liblib-gap-validation.md#13-授权后续轮真实执行负例和恢复边界)。主要纠正如下：

- 单次H3真实运行：UI/存储/报价/创建均5s、768P、16:9、1个、有声；成片元数据5.167s、1344×768。已受理后断网重连，唯一创建请求、同任务完成；不证明丢失创建响应后的幂等重试。本续轮总报价/可见余额变化130（两正文60＋视频70）。
- 预设改值取消恢复、停靠刷新及1440/768/375三宽度的关键控件可达已补；不能推断所有未发送草稿都跨刷新恢复。

- Skill实际发布、私有详情有snapshot/version/auditStatus，官方分享页匿名可读源码与合成样例；用户单独授权后删除了合成“连续性清单”，私有列表移除，原分享页匿名重读返回HTTP200/code10051“数据不存在”并显示失效。整体删除可使本样例公开详情失效，但没有单独撤回或归档恢复证据；不能将HTTP200视为业务成功，也不能推断已分发副本一并销毁。合成聊天分享仍未撤销，详细证据见补证§13.5。
