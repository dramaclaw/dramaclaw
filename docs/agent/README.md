# AI 协作运行手册

这套文档解决的不是“让 AI 多写一点总结”，而是三个工程问题：换模型后如何恢复上下文、
多条工作线如何避免覆盖、一个方案如何从提出到验收都能追溯。根 `AGENTS.md` 是强制规则，
本文件解释其运行方式。

## 一、四层信息，各自只负责一件事

| 层 | 权威内容 | 更新频率 | 不该放什么 |
|---|---|---|---|
| `AGENTS.md` | 所有模型必须遵守的稳定规则、构建与仓库边界 | 低 | 某条任务的当前进度 |
| `STATE.md` | 在途工作线、全局阻塞、冲突雷达、恢复顺序 | 高 | 详细方案和长篇取证 |
| `tasks/<slug>.md` | 单条线的目标、方案、写入边界、决策、进度、验收 | 高 | 跨任务通用规则 |
| `claims/<slug>.toml` | 机器可读基线、独占 / 共享 / 只读路径 | 随方案 | 状态、进度、长篇理由 |
| `docs/guides/<slug>.md` | 调研证据、竞品比较、协议细节、长篇设计 | 按需 | 每日状态和重复的待办 |

代码和测试仍是最终行为事实。文档说明“为什么、做到哪、下一步是什么”，不复制实现细节。
同一结论只能有一个权威落点；其他文件用链接引用。若两处内容冲突，先修正权威文件，再删掉副本。

## 二、工作线状态机

只使用以下状态，避免“基本完成”“代码都在”等无法比较的自由文本：

| 状态 | 含义 | 允许做什么 |
|---|---|---|
| `提案中` | 目标存在，但证据、范围、方案或验收不完整 | 只读调研和写方案，不改业务代码 |
| `方案就绪` | 方案门已满足，尚未开始实施 | 可以认领并开始 |
| `执行中` | 正在按方案修改 | 只能写入台账声明的范围 |
| `待验收` | 实现完成，仍缺测试、实机或用户验收 | 只做验收与针对性修复 |
| `已阻塞` | 无法继续，且阻塞条件已写清 | 只处理解除阻塞所需动作 |
| `已完成` | 验收标准全部满足，无未解释 diff | 准备归档 / 合并 |
| `已归档` | 已从活动索引移出 | 默认不再改；新问题开新线 |

状态只表达生命周期，环境问题写在「阻塞」里。实现完成但缺密钥真机验证，应是 `待验收`，
不是“已完成”；方案不完整时不允许直接跳到 `执行中`。

## 三、代码前方案门

一个方案可执行，至少要回答以下问题：

1. **为什么做**：用户可感知结果是什么，怎样算完成？
2. **不做什么**：哪些邻近问题明确不在本轮，防止范围漂移？
3. **从哪里开始**：当前提交、上游差距、已有脏文件和已有实现是什么？
4. **改哪里**：列出精确路径，并标记独占、共享、只读。
5. **如何做**：按依赖顺序列步骤，每步有可观察的完成条件。
6. **会破坏什么**：API、数据、UI、发行边界、配置和兼容性风险是什么？如何回退？
7. **如何证明**：自动测试、静态检查、手工路径和期望结果分别是什么？
8. **是否重复**：本地其他工作线、远端分支、`origin/main` 是否已有同类实现？

小修不用写论文，但这八个问题仍要在现有台账中用短句回答。只有调研、解释、代码审查且不改文件时，
可以不新建工作线；一旦准备写业务代码，就要先落台账。

## 四、写入边界与冲突处理

### 三种路径模式

- `独占`：只有本工作线可以修改。另一条执行中工作线也声明同一路径时，方案门失败。
- `共享`：多个工作线确实需要修改。必须写清先后顺序、接口归属和最终集成者，串行修改。
- `只读`：用于理解或验证，但本轮承诺不改；发现必须修改时先更新方案。
- `coordination`：STATE / 台账等协调文件，不参与业务代码锁冲突。

路径尽量精确到文件。只有整个新目录明确属于本工作线时才写 `path/**`；不要用 `frontend/src/**`
这种等于没划边界的范围。

### 动手前的最小冲突审计

```bash
git status --short --branch
git log -1 --oneline
git diff --name-only
git diff -- <准备修改的路径>
git diff --name-only HEAD..origin/main -- <准备修改的路径>
git branch --all --list '*关键词*'
```

远端引用可能不是最新的；需要 fetch 时只更新引用，不在脏工作区直接 pull/rebase。发现重叠后：

1. 在 STATE 冲突雷达登记路径、涉及工作线和远端来源。
2. 对比行为、测试和提交历史，判断是同一实现、互补实现还是冲突实现。
3. 在台账记录选择：复用、移植、串行合并、放弃；写清为什么。
4. 未作选择前不得继续写重叠文件。

### 同一个脏工作区的临时纪律

当前遗留现场尚未拆线，同一共享文件只允许一个会话写。其他会话可以只读分析，但不能同时修。
不要把未提交改动复制粘贴进另一个 worktree 后继续，因为来源和基线会丢失。

完成遗留清理后，默认一条工作线一个分支 / worktree：从明确提交创建、只带该线提交、合并前与主线对账。
worktree 是隔离工具，不是未提交改动的备份工具。

### 可执行 guard（所有客户端通用）

`scripts/agent_guard.py` 只依赖 Python 标准库，依赖安装前就能运行。标准顺序：

```bash
# 1. 恢复现场：STATE、台账、scope、脏文件归属必须自洽
python3 scripts/agent_guard.py check
python3 scripts/agent_guard.py status

# 2. 方案与 scope 更新完成、台账状态为「执行中」后取得锁
python3 scripts/agent_guard.py acquire <slug> --owner <client/session-id>

# 3. 每批写入前检查精确路径
python3 scripts/agent_guard.py preflight <slug> --owner <client/session-id> \
  --path path/to/file --path path/to/another

# 4. 记录进展与验证后检查交接，再释放锁
python3 scripts/agent_guard.py handoff <slug> --owner <client/session-id>
python3 scripts/agent_guard.py release <slug> --owner <client/session-id>
```

guard 会 fail closed：STATE / 台账状态不一致、必填章节缺失、基线漂移、任意脏文件未被认领、
独占路径重叠、共享声明不是双方互认、任务不是「执行中」、锁归属不符、请求路径越界，都会返回 `BLOCKED`。

锁放在被 Git 忽略的 `.agent-locks/`。同一检出目录采用**单写者**：任何任务持锁时，第二个任务即使路径不重叠
也不能 acquire；需要并行就开独立 worktree。不同客户端只要共享同一个检出目录，就共享这把原子锁；
跨机器并发仍必须依靠独立分支 / worktree 与 PR。非「执行中」工作线可以持锁更新 coordination 路径，
但 guard 仍拒绝它 preflight 业务代码。

acquire 会记录台账和已认领脏文件的 SHA-256 快照。handoff 比较当前快照；本会话改过认领文件却没改变台账内容时失败。
release 会再次执行 handoff，所以不能跳过交接直接解锁。锁目录不承载项目事实，`--force` 仅用于确认原会话已经结束后的恢复。
锁内完成最终提交后，handoff / release 允许 `HEAD` 从取得锁时的提交**单向快进**，因此正常流程可以是
`acquire → 修改并记台账 → commit → handoff → release`。如果发生 reset、rebase、切到分叉历史或锁内
提交了代码却没更新台账，仍然 fail closed。提交后若还要继续写业务文件，应先 release，更新该线基线并重新 acquire；
不能利用“快进可交接”绕过下一批写入的基线审计。

## 五、一次标准会话

### 开始

1. 读 STATE 和目标台账，核对 Git。
2. 运行 guard `check` / `status`，检查目标路径的现有 diff 与远端重叠。
3. 若接手已有线，在台账写本次要完成的一个可验收切片；若新开线，复制模板、创建同名 scope 并登记 STATE。
4. 方案门完整后才把状态改成 `执行中`，然后 acquire 并对精确路径 preflight。

### 实施

1. 先改最小闭环，不跨出写入边界。
2. 计划变化时先改台账：原计划、发现、决定、影响。
3. 一次只解决当前工作线的问题；陌生问题登记为待办或新线，不顺手扩张。
4. 先跑聚焦测试，再跑相关门禁；失败要区分本轮回归、存量失败和环境阻塞。

### 结束

1. 检查 `git diff --name-only`，每个本轮改动都能归到台账。
2. 在最新进展中写文件 / 行为、理由、验证命令与结果。
3. 更新决策、待办、阻塞和下一步；下一步要能直接执行。
4. 同步 STATE 的状态、冲突与恢复顺序。
5. 运行 guard `handoff`；通过后 release。只有验收全过且无未解释 diff 才标 `已完成`；
   归档后从 STATE 活动表删除，并删除或归档对应 scope。

## 六、当前仓库的恢复策略

当前不是适合直接“同步主线”的普通工作区：本地 `main` 落后远端，六条业务线交织在百余个脏条目中，
其中若干实现已出现在远端功能分支。安全顺序是：

1. **先冻结交接文档**：让每条改动有名字、边界、决策和验收。
2. **逐线做来源审计**：本地 diff 对比相关远端分支与 `origin/main`，确认哪些已提交、哪些仅本地、哪些分叉。
3. **按依赖拆提交**：优先新增的纯模块和测试，再拆共享适配层；每个提交只属于一条线并通过针对性验证。
4. **建立可恢复锚点**：把拆好的提交推到对应分支；本地生成物与密钥另行备份，不混进 Git。
5. **最后同步主线**：在干净、可回退的分支 / worktree 中合并或 rebase，并逐个解决已登记热点。

在第 3 步完成前，不建议启动新的大功能。新需求先进入 `提案中`，避免继续扩大交叉面。

## 八、记录质量示例

坏记录：`优化了画布性能，测试通过。`

好记录：`修改 Canvas.tsx 的视口内节点筛选，在缩放 < 0.35 时只挂载 LodShellNode；没有改节点数据结构，
因为该线只处理渲染成本。运行 pnpm test -- canvas-lod.test.ts 全绿；100 节点手工 FPS 尚未测，状态保持待验收。`

后者能让下一任模型判断哪些行为已定、哪些尚未证明，也不会把“没测”误认为“已经完成”。
