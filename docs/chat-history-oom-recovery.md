# 聊天历史 OOM 修复与存量恢复

本次修复阻断自动重连触发的历史加载 OOM，不改变模型生成的内容，也不增加模型复读中止阈值。

## 新写入与读取

- `assistant.message_parts` 在 SQLite `BEGIN IMMEDIATE` 事务内按 turn 合并、更新。其他事件仍独立保留。
- 本地缓存及服务端历史通过只读 hydration 更新界面，不创建持久化意图。只有实时消息与用户编辑创建内存内的保存标记，标记捕获原始 scope 和内容，不序列化进缓存。
- 浏览器在 React 提交后消费这些保存标记，500 ms 合并提交；非 busy、切换 scope 和卸载时刷新队列。请求串行发送，失败最多重试三次并保留待提交快照，界面显示错误。关闭浏览器时网络请求不能保证完成。
- 带 `snapshot_revision` 的旧版本不能覆盖新版本。服务端无版本的写入仍允许执行，并继承已有版本。当前浏览器版本使用本机时间及递增序号，不提供跨设备时钟偏差下的严格因果排序。
- 单事件及合并快照限制为 8 MiB（实测正常 31 分钟 turn 的合并快照约 1.48 MiB）；超限返回 HTTP 413，事务回滚，保留已落盘的上一版，不截断原内容。前端收到 413 后不再重试该 turn，只提示一次保存失败。
- 历史只读取当前消息对应的 turn，每 turn 最多 8 MiB，全次最多 16 MiB 编码 payload。行数上限按类型分开：`assistant.message_parts` 最多 256 行（只有未压缩的旧库会超过），其他 UI 事件（如 `canvas_context_result`）最多 4096 行，主要靠字节预算约束。SQL 在传输大字段前检查字节数；从最新事件向前读取，再按原顺序合并。超限返回 `parts_incomplete`，界面显示部分历史未加载，正文保留。
- 上述预算限制 UI 事件，不是整个进程 RSS 上限。部署仍应保留容器内存上限。

## 存量库

上线读取兜底后，大库不会因 UI 事件整表加载而再次触发原故障，但部分历史可能降级；超过写入合并预算的旧 turn 会明确拒绝快照写入，需先离线压缩。

先停止访问目标库的所有写入进程，并完整备份 SQLite（包括未 checkpoint 的 WAL，或使用 SQLite backup）。不要仅复制正在写入的主库文件。

在仓库环境下检查：

```bash
python scripts/compact_chat_ui_events.py /path/to/chat.db
```

确认备份可用且写入已停止后执行：

```bash
python scripts/compact_chat_ui_events.py /path/to/chat.db --apply
```

工具逐行回放原有 parts 合并逻辑，在临时表保存每个 turn 的结果，然后事务内替换快照、保留其他事件和正文，提交后执行 VACUUM。遇到无效 JSON 或超过预算的快照会回滚合并事务；VACUUM 若失败，已提交的合并结果仍有效，但空间可能尚未回收。预留 VACUUM 所需磁盘空间。禁止直接用“只留最后一行”代替合并。

验证：原有角色/工具/思考 parts 保留、正文不变、多次打开和重连不再 OOM。完成前保留备份及容器内存上限。

限制：这是本机存储层压力测试，未启动完整 API/浏览器，也未使用真实事故数据。不能把这些 RSS 数字当作整个 API 的内存上限或线上容量结论。本机剩余磁盘不足以安全构造 19.5 GiB 库并完成压缩，故用相同事件数量、较小平均快照及事故级终态消息验证。

## 浏览器网络链路复现（2026-11-10）

使用 `scripts/acceptance/chat_oom_replay.py` 提供仅监听 127.0.0.1:18791 的临时服务，Vite 在 5198 代理到该服务，浏览器打开 `/e2e/chat-oom.html`。

复用实际 `useSuperChat` hook、HTTP 客户端、快照队列、`append_chat_ui_event`、`_send_scope_changed`、`_history` 及 SQLite 存储。测试页面显示 hook 的状态，不挂载完整聊天面板；WebSocket 接收分发由测试服务提供，登录与项目解析使用固定测试上下文，模型调用替换成确定性的思考增量。因而这是浏览器网络链路集成复现，不是生产部署或真实模型验收。

步骤及实测结果：

1. 加速发送 46,930 个 `agent.thought.delta`，累计 538,638 字符，再发送 `chat.done`。实际 HTTP 保存请求 121 次，最终快照只有 1 行、539,008 字节，已保存思考字符数准确为 538,638。
2. 服务端主动关闭 WebSocket 10 次，由实际前端自动重连。保存请求仍为 121、快照仍为 1 行；重连后的界面思考字符数为 538,638。
3. 向这个隔离临时库注入旧式累计快照（仅测试脚本 `--seed-fixture` 操作）：46,931 行，数据库 2,304,692,224 字节，payload 合计 2,268,781,154 字节，最后一份仍为原终态快照。
4. 重新加载浏览器页面，再主动断线并自动重连 10 次。累计连接 22 次、历史加载 45 次，API 持续可用，保存请求数仍为 121，库行数未增加。界面显示“此对话的部分历史内容过大，已限制加载”；连接正常、busy=false、思考字符数 538,638。
5. 后端进程峰值 RSS：开始回放前 429,588,480 字节；回放及两组重连后 430,424,064 字节（约 410.48 MiB）。这包含真实 chat route 模块及依赖的导入开销，不能与存储层单独子进程的 RSS 混为一谈。

上述回放是加速压力场景，没有让模型真实复读 23 分钟，也没有启动旧版无界读取来故意触发整机 OOM。它验证的是修复后的存储不再累积全文快照，以及已有膨胀库经过浏览器重连能够有界降级。真实 19.5 GiB 事故库、生产鉴权和完整聊天面板仍未覆盖。
